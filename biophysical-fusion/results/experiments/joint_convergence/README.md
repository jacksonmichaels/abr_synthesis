## The question

`full_run` concluded that joint models sit at **−0.0116 vs the published MD-CNN**
on DNA alone ("parity at best"). That number was measured on models that were
still improving when the epoch cap hit:

| scope | median `best_epoch` | folds at the cap (≥140 of 150) |
|---|---|---|
| single-drug | 20 | 0.7–2.5% |
| joint `late_fusion` | 124 | **40%** |
| joint `mdcnn` | 123 | **28%** |

`multidrug_dna__late_fusion` fold 0 went ep50 0.8727 → ep100 0.8969 → ep146
0.9100 — no plateau, still climbing at the wall. So the single-drug numbers come
from converged models and the joint numbers do not, and the whole §2/§4
comparison is confounded by that.

**But** `LR = exp(-9) ≈ 1.2e-4` (`training/multimodal.py`) is roughly 10× below a
normal Adam setting, so this may be a learning-rate problem wearing an epoch-cap
costume. Those two have opposite cost consequences — 400 epochs makes the grid
~2.5× more expensive, a usable LR makes it *cheaper* — which is exactly why this
is a 6-job pilot on one cell and not a 20-cell grid.

## The cell

`multidrug dna__late_fusion` — the §2 reference point (full_run joint CV
**0.9132**, the best joint DNA-only cell) and the one showing the cap problem.
`cisfusion` converges around epoch 85 and would not have exposed it.

## The arms — each changes exactly ONE thing vs a0

| arm | change | asks |
|---|---|---|
| `a0_control` | none (exact full_run settings) | reproduces 0.9132? confirms the new defaults are unchanged |
| `a1_ep400` | `--epochs 400` | is it an epoch-budget problem? |
| `a2_lr1e3` | `--lr 1e-3` | or a learning-rate problem? |
| `a3_lr1e3_reg` | `--lr 1e-3 --dropout 0.3 --weight-decay 1e-4` | does a faster LR need regularization? (46M params, 17.9k isolates, currently none) |
| `a4_patience30` | `--patience 30` | was patience=15 firing spuriously? (`all_modalities__mdcnn` fold 1 stopped at epoch 36 scoring 0.8609 against siblings at 0.918) |
| `a5_monitor500` | `--monitor-min-n 500` | how much of the stop signal is LEVOFLOXACIN noise? (n=269, ~15 resistant per val fold, contributing 1/11 of an unweighted macro) |

`a0` deliberately duplicates a cell `full_run` already has. It costs ~13 h and
buys two things: an empirical check that the refactor left defaults untouched,
and the only baseline with **saved weights**.

## Reading it

Compare each arm's `cv_macro_auc_mean` against `a0_control`, and check
`best_epoch` per fold to see whether the arm actually removed the ceiling. An
arm that improves CV *and* stops before its cap has converged; an arm that
improves CV while still pinned at the cap has not, and needs more budget still.

```bash
python - <<'EOF'
import json, glob
for p in sorted(glob.glob("*/multidrug__*.json")):
    j = json.load(open(p))
    print(f"{p.split('/')[0]:44s} cv={j['cv_macro_auc_mean']:.4f} "
          f"+/-{j['cv_macro_auc_std']:.4f} epochs={[f['best_epoch'] for f in j['cv_folds']]}")
EOF
```

**Fold SD in `full_run` was 0.003–0.030 against a gap of 0.0116.** One seed, five
folds. Treat any arm-vs-a0 difference under ~0.01 as unresolved rather than real
— see the closing section of `../CODE_CHANGES_20260806.md`.

## What this run does NOT do, on purpose

- **No `--all-regulatory`.** The pilot cell is DNA-only, so it would be a no-op.
  Widening the promoter set is the highest-value change identified in the audit
  (ISONIAZID loads 2 of 14 WHO regions, KANAMYCIN 1 of 7 and loses the `eis`
  promoter) and is the **recommended next submission** — but running it at a
  training setting we are about to change would waste it. Gate it on this run.
- **No multi-seeding.** These are one-variable diagnostics. Multi-seeding the
  joint headline cells is the prerequisite for reporting any joint result and
  should follow.
- **No capacity changes.** That is `../joint_capacity/`, deliberately kept
  separate so a margin can be attributed to one or the other.
